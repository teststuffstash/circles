# Bake pipeline — data.json generation

**CIR-PROCESS-BAKE** — The bake job evaluates adapters and produces the static render inputs.

## Bake overview

The bake pipeline is the (eventually nightly) job that:
1. Reads `circles.yaml`
2. Evaluates each item's adapter (freshness scans files, command runs scripts, manual passes through)
3. Resolves each item's status color
4. Writes `data.json` (the baked render input)
5. Writes the static `index.html` page

## Phases

| phase | what bake does | status source |
|---|---|---|
| P0 | No bake: `data.json` is hand-written or statically generated from `circles.yaml` manual statuses only | `manual:` only |
| P1 | Full bake: evaluates `freshness:` and `command:` adapters, writes `data.json` | all adapter types |
| P2 | Bake also extracts metric series for detail pages | all + metric extraction |

**CIR-PROCESS-BAKE-P0** — In P0, the page reads `data.json` directly. The `data.json` may be hand-written (for bootstrapping) or generated by a simple script that reads the manual statuses from `circles.yaml`.

⚖ **AMBIGUITY: P0 data path.** Options: (a) P0 page reads `circles.yaml` directly (no bake, no data.json); (b) P0 has a minimal bake that converts `circles.yaml` manual statuses to `data.json`. **Recommendation:** (b). Rationale: the page reads `data.json` from day one — the same data contract from P0 through P2. This avoids a P0→P1 data-path migration. The P0 bake is trivial (just reads manual statuses and writes JSON) but establishes the contract.

## data.json schema

**CIR-PROCESS-BAKE-SCHEMA** — The baked `data.json` has this structure:

```json
{
  "person": "Alex Example",
  "generated_at": "2026-08-03T19:00:00Z",
  "rings": [
    {
      "id": "self",
      "label": "① Self",
      "items": [
        {
          "id": "sleep",
          "label": "Sleep",
          "status": "ok",
          "guardrail": "Lights out by 23:00 on weeknights",
          "detail": "Last data: 2026-08-01",
          "link": null,
          "share": null
        }
      ]
    }
  ]
}
```

### data.json field decision table

| field | type | description |
|---|---|---|
| `person` | string | Display name from circles.yaml |
| `generated_at` | string (ISO 8601) | When this bake ran |
| `rings` | array | Ordered inside-out (same as circles.yaml) |
| `rings[].id` | string | Ring slug |
| `rings[].label` | string | Ring display label |
| `rings[].items` | array | Items in this ring |
| `rings[].items[].id` | string | Item slug |
| `rings[].items[].label` | string | Item display label |
| `rings[].items[].status` | string | One of: `ok`, `attention`, `act`, `unmonitored` |
| `rings[].items[].guardrail` | string or null | Guardrail text (null if absent) |
| `rings[].items[].detail` | string | Hover detail line (adapter-specific) |
| `rings[].items[].link` | string or null | Click target URL |
| `rings[].items[].share` | number or null | Arc weight |

**CIR-PROCESS-BAKE-GENERATED-AT** — The `generated_at` field is an ISO 8601 datetime in UTC.

⚖ **AMBIGUITY: generated_at format.** Options: (a) ISO 8601 with timezone `2026-08-03T19:00:00Z`; (b) ISO 8601 date only `2026-08-03`; (c) Unix epoch timestamp. **Recommendation:** (a). Rationale: full datetime is needed for staleness display ("this page was baked 6 hours ago"); ISO 8601 is human-readable and machine-parseable.

## Bake warnings

**CIR-PROCESS-BAKE-WARNINGS** — The bake job produces warnings (on stderr) for:
- Freshness source file missing or empty
- Command adapter non-zero exit
- Command adapter unexpected output
- Item with no adapter (⚪ unmonitored — informational, not an error)

Warnings are non-fatal. The bake still produces `data.json` with ⚪ status for warned items.

## Bake error handling

### Error decision table

| description | inputs | expected |
|---|---|---|
| circles.yaml not found | missing config file | Bake fails with error (no output) |
| circles.yaml invalid YAML | malformed YAML | Bake fails with parse error |
| circles.yaml valid YAML, invalid schema | missing `rings:` key | Bake fails with schema validation error |
| adapter returns invalid color | command prints "blue" | ⚪ + warning (non-fatal) |
| all adapters in a ring warn | ring with all warnings | Bake succeeds; all items ⚪ in data.json |

## Deployment pipeline integration

**CIR-PROCESS-BAKE-DEPLOY** — The bake job's output (`data.json` + `index.html`) replaces the vanilla `public/index.html` at build time:
1. Bake produces `public/index.html` and `public/data.json`
2. Dockerfile copies `public/` to nginx
3. Helm chart deploys the image

This replaces the vanilla placeholder and is the same image-building pipeline that exists today.

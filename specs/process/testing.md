# Testing — tiers, and how a spec row becomes a test

## CIR-PROC-TEST-TIERS — the ruled terminology <a id="cir-proc-test-tiers"></a>

This vocabulary is **ruled and recorded, not re-litigated**:

| tier | means |
|---|---|
| **unit** | pure logic, no external components |
| **system testing** | the logic against **real components in a local cluster (kind)** |
| **e2e** | the actual target environment |

"Integration" is not a tier here; do not use the word. A test that needs a real component but not
a cluster is described by what it needs, not by inventing a fourth name (see ⚖ CIR-Q-32).

| description | inputs | expected |
|---|---|---|
| resolution logic is unit | freshness age arithmetic, status tables | unit tests over decision-table rows |
| schema validation is unit | config error rows | unit |
| the chart is system-tested | chart rendering + install | the existing chart unit tests plus a kind install ([CIR-PROC-GATE](#cir-proc-gate)) |
| the deployed page is e2e | the real target environment | e2e |
| no tier is skipped by moving a requirement | any requirement | the tier follows what the requirement actually needs |

## CIR-PROC-TEST-ROWS — a row is a test <a id="cir-proc-test-rows"></a>

Every decision-table row in this tree is written to be executable: `description` becomes the test
id verbatim, `inputs` becomes the fixture, `expected` becomes the assertion.

| description | inputs | expected |
|---|---|---|
| a row's description is the test id | row "freshness stale" | test id contains `freshness stale` verbatim |
| a test names its requirement | any test | the `CIR-*` id appears in the test (id or marker), so a requirement's coverage is greppable |
| rows are parametrised, not copy-pasted | 12 rows in one table | one parametrised test, 12 cases — never 12 near-identical functions |
| inputs are built from the table at run time | any test | no hidden or binary fixtures ([fixtures/README.md](../../fixtures/README.md)) |
| a fixture person row is reused, not duplicated | rows citing the fixture | the test reads `fixtures/alex/`, it does not restate the YAML inline |
| dates are injected, not "today" | freshness tests | a fixed reference date ([CIR-BAKE-DETERMINISM](../data/data-json.md)) so committed fixture dates stay readable |
| an unevidenced requirement is not marked | any requirement without a test | nothing is written in the spec; coverage is derived by grepping ids, never declared |

**Verified-ness is derived.** No page in this tree carries ✓/🚧. If a coverage report is wanted,
it is generated by matching `CIR-*` ids in `specs/` against ids referenced in tests — a
computation, not a claim an author can make.

## CIR-PROC-GATE — what `devbox run ci` must grow <a id="cir-proc-gate"></a>

`scripts/ci.sh` is the one place the gate grows (`CLAUDE.md`). Today it is chart validation plus
chart unit tests. As the product lands, the gate must gain — in this order, cheapest first:

| description | inputs | expected |
|---|---|---|
| spec ids are unique | two requirements with one id | gate fails |
| spec links resolve | a link to a missing page or anchor | gate fails |
| every ⚖ has an id and appears in the index | a `⚖` with no `CIR-Q-*`, or missing from `open-questions.md` | gate fails |
| resolution logic is unit-tested | bake package | unit tests run |
| the built page meets its asset budget | built `index.html` | gate fails past the budget ([CIR-RENDER-ASSET-BUDGET](../render/layout.md)) |
| the built page has no external origins | built page | gate fails on any third-party URL ([CIR-RENDER-NO-EGRESS](../render/layout.md)) |
| the artifact matches its schema | `data.json` | validated against the shape in [CIR-BAKE-ARTIFACT](../data/data-json.md) |
| secrets scan stays clean | any change | `devbox run scan-secrets` |

The first three are cheap text checks that keep *this tree* honest and are the natural first
additions — they are the only gate steps a spec-only PR can be judged by today.

## CIR-PROC-BROWSER-EVIDENCE — the render requirements need a browser <a id="cir-proc-browser-evidence"></a>

A large share of this tree's requirements — one screen, one A4, print backgrounds, contrast,
focus order, no-JS rendering, touch targets — cannot be evidenced by any of the three tiers as
they stand. They need a real browser rendering the built page, which is neither pure logic nor
a cluster.

| description | inputs | expected |
|---|---|---|
| render requirements state their evidence path | any `CIR-RENDER-*` | a headless-browser check, not a unit assertion |
| no render requirement is asserted from source alone | e.g. print colour | grepping for `print-color-adjust` is not evidence that the fills print |
| screenshots are not the assertion | any visual requirement | the assertion is a measurable property (no scroll, page count, computed contrast), not an image someone eyeballs |

⚖ **CIR-Q-32 — where do browser checks live in the ruled tiers?** Options: (a) call them *unit*
tests over a headless browser, since no cluster is involved — stretches "pure logic";
(b) call them *system testing*, since a real component (the browser) is involved, and accept
that the "in kind" clause does not apply — stretches the ruling; (c) run them inside kind
(a browser pod against the deployed nginx), making them system tests by the letter of the
ruling; (d) name a fourth tier. *Recommendation: (c) where it is cheap and (b) otherwise, and
put the question to the ruling's owner rather than inventing (d).* Nothing in this repo runs a
browser today, and the ride's platform card is explicit that docker-backed gates run in GitHub
CI, not on the agent host — so this is a real gate-capability gap, not a naming quibble.

## CIR-PROC-BUG-CROSSES-AS-A-ROW <a id="cir-proc-bug-crosses-as-a-row"></a>

A reported defect enters this repo as a **new decision-table row** that fails against the old
behaviour and passes against the new one, in the spec page that owns the requirement — then as
the test that row generates. A fix without a row is not a fix; a row that could not have caught
the defect is not a regression test.

| description | inputs | expected |
|---|---|---|
| a bug becomes a row first | reported wrong status | new row in the owning table, plus its test |
| the row is failing before the fix | new row, old code | red |
| real data never crosses the boundary | a defect found on a real person's config | reproduced as synthetic fixture rows only ([CLAUDE.md](../../CLAUDE.md)) |
